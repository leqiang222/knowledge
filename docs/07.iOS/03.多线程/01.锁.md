# iOS多线程安全-锁

### 为什么要线程安全

多个线程访问同一块资源的时候，很容易引发数据混乱问题。出现线程安全的原因就是在同一个时间，多个线程同时修改一个值。

最常用的就是互斥锁，当然还有很多种不同的锁，比如自旋锁、读写锁、乐观锁等，不同种类的锁自然适用于不同的场景。

如果选择了错误的锁，那么在一些高并发的场景下，可能会降低系统的性能。

### 自旋锁和互斥锁

##### 互斥锁

- **互斥锁**加锁失败后，线程会**释放 CPU** ，就交给操作系统管理，让操作系统去告知可以加锁。所以互斥器的加锁操作通常都需要涉及到上下文切换，操作花销也就会比自旋锁要大。

##### 自旋锁

- **自旋锁**加锁失败后，会一直cpu占用资源，线程不会休眠，会一直`循环`去看能不能加锁，直到它拿到锁，所以效率最高；  

##### **读写锁**

- 读写锁既可以选择互斥锁实现，也可以基于自旋锁实现
- 它由「读锁」和「写锁」两部分构成，如果只读取共享资源用「读锁」加锁，如果要修改共享资源则用「写锁」加锁

##### 乐观锁与悲观锁

- 互斥锁、自旋锁、读写锁，都是属于悲观锁
- 悲观锁做事比较悲观，它认为**多线程同时修改共享资源的概率比较高，于是很容易出现冲突，所以访问共享资源前，先要上锁**。
- 那相反的，如果多线程同时修改共享资源的概率比较低，就可以采用乐观锁。

### 几种常见的锁

##### OSSpinLock 自旋锁

- **ios10**之后过期

##### os_unfair_lock 互斥锁

- **ios10**之后支持

##### ptheard_mutex 互斥锁

递归锁 PTHREAD_MUTEX_RECURSIVE

递归锁 PTHREAD_MUTEX_DEFAULT

##### NSLock

对 mutex PTHREAD_MUTEX_DEFAULT 普通锁的封装

##### NSRecursiveLock

对mutex PTHREAD_MUTEX_RECURSIVE 递归锁的封装

##### NSCondition

对mutex和cond的封装

##### NSConditionLock

对NSCondition的封装

##### Dispatch_semaphore

可以控制线程的个数 当控制线程个数为1的时候 能确保同时只有1条线程去访问，已达到确保线程安全的目的。

```objectivec
dispatch_semaphore_t semaphore = dispatch_semaphore_create(1);

// 如果信号量<=0 当前线程就会进入休眠状态 直到信号量的值>0
// 如果信号值>0 就-1 然后执行下面代码
dispatch_semaphore_wait(self.semaphore, DISPATCH_TIME_FOREVER);
[super __saleTicket];
// 信号量+1
dispatch_semaphore_signal(_semaphore); 
```

##### dispatch_queue(DISPATCH_QUEUE_SERIAL)

串行队列,当在一个串行队列执行的时候，只有一个线程，能确保线程安全

##### @synchronized

os_unfair_recursive_lock的封装
